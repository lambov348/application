# MöbelStock24 — внутренняя платформа

Реализация по `TZ_MobelStock24_Platform.md` (в корне репозитория).
Текущее состояние: **Этап 0 завершён, Этап 1 идёт** — куски 1–7 из 10: каркас, база, миграции, вход с ролями и 2FA, управление сотрудниками, установка на телефон, клиенты и адреса, заявки и канбан, календарь и диспетчеризация, предложения клиенту.

Старое приложение (публичная форма заявок) живёт в корне репозитория и не
затрагивается.

## Запуск

### Через Docker (рекомендуется)

```bash
cd apps/platform
cp .env.example .env

# Секреты. Без них приложение намеренно не стартует.
echo "AUTH_SECRET=\"$(openssl rand -base64 32)\""      >> .env
echo "ENCRYPTION_KEY=\"$(openssl rand -base64 32)\""   >> .env
echo "POSTGRES_PASSWORD=\"$(openssl rand -hex 16)\""   >> .env

docker compose up -d postgres redis
docker compose run --rm app npx prisma migrate deploy
docker compose up -d app
```

Открыть http://localhost:3000

### Первый вход

В базе нет ни одного пользователя и нет сидов с выдуманными людьми. Первого
владельца создаёт скрипт — он спросит имя, email, роль и пароль:

```bash
docker compose run --rm app npm run create-user
# без Docker:  npm run create-user
```

Роль `INHABER` не пускает в систему без второго фактора (глава 4 ТЗ). При
первом входе форма предложит перейти на `/login/2fa-einrichten`: там появится
QR-код для Google Authenticator, Aegis, 1Password или подобного приложения,
а после подтверждения — десять кодов восстановления. **Коды показываются
ровно один раз**, сохраните их.

Дальше сотрудников заводит владелец в разделе «Benutzer» — командная строка
больше не нужна.

### На сервере (продакшен)

Пошаговая инструкция — **[deploy/README.md](deploy/README.md)**: от пустого
сервера Hetzner до работающей платформы, с брандмауэром, HTTPS, бэкапами
и проверкой восстановления.

Коротко:

```bash
cd apps/platform
cp deploy/.env.example deploy/.env   # заполнить домен и секреты
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env \
  run --rm -it migrate npm run create-user
```

### Без Docker

Нужен PostgreSQL 16. В `.env` замените в `DATABASE_URL` хост `postgres` на `localhost`.

```bash
cd apps/platform
npm install
npx prisma migrate dev
npm run dev
```

## Дымовые проверки

Проверяют то, что не ловится юнит-тестами: установку на телефон, вход без
JavaScript, разделение доступа по ролям и скорость.

```bash
npm run build && npm start          # в одном окне

# в другом; учётные данные берутся из окружения и в репозиторий не попадают
SMOKE_URL=http://localhost:3000 \
SMOKE_MONTEUR="max@firma.de:пароль" \
SMOKE_DISPONENT="petra@firma.de:пароль" \
SMOKE_INHABER="chef@firma.de:пароль:секрет2FA" \
SMOKE_LEAD_SECRET="$LEAD_WEBHOOK_SECRET" \
npm run smoke
```

`SMOKE_URL` должен совпадать с `AUTH_URL` приложения: Auth.js строит обратные
ссылки по `AUTH_URL`, и при разных именах хоста (`localhost` против `127.0.0.1`)
сессия не доедет.

Сейчас проверок 123: от установки на телефон до подписи клиента на экране
и приёма заявки с сайта.

Без переменных с учётными данными проверки входа пропускаются, остальные
выполняются.

**Только на базе для разработки.** Проверки заводят тестового клиента
с адресом — на рабочей базе это оставит мусор. Тестовые клиенты узнаются
по фамилии вида `Smoke123456`.

## Отклонения от главы 7 ТЗ

| Что | Как в ТЗ | Как сделано | Почему |
|---|---|---|---|
| `leads` и `deals` | две таблицы | одна `Deal` | Канбан главы 5.2 — одна лента колонок на обе стадии. Две таблицы дали бы два поля `status` и вопрос, какое из них на карточке. |
| Деньги | тип не указан | `Int`, центы | Требование заказчика. Брутто не хранится: вычисляется из нетто и ставки, иначе хранимая копия разойдётся с расчётом. В `Offer` суммы заморожены снимком — это документ. |
| Ставка НДС | `vat_rate` | `vatRateBp`, базисные пункты | 19 % → `1900`. Целое число вместо дроби. |
| `price_approved` | `bool` | + `priceApprovedAt`, `priceApprovedById` | Через полгода нужно уметь показать, кто и когда одобрил цену. |
| Назначение на выезд | только `team_id` | + `AppointmentAssignee` | Правило «Monteur видит только свои заказы» становится строкой в запросе, а не вычислением через членство в бригаде. |
| Статусы выезда | два разных набора (5.3 и 5.6) | объединение, 6 значений | В 5.3 отсутствует `ANGEKOMMEN`. |
| `addresses.lat/lng` | есть | убрано | Предупреждение «мало времени на переезд» без геокодинга не посчитать, а геокодинг — внешний сервис и отдельный вопрос по DSGVO. Вместо него `Settings.travelBufferMinutes`. Вернём в Этапе 2. |
| `activity_log` | таблица | + поле `ip`, только вставка | IP нужен для фиксации согласия с Angebot (глава 5.4). Неизменяемость держит триггер в базе. |
| Даты | не указано | `timestamptz` везде | Prisma по умолчанию создаёт `timestamp without time zone`, где смещение не хранится, и любой внешний инструмент истолкует время по своему часовому поясу. |
| Сессии Auth.js | таблицы адаптера | JWT + `User.sessionsValidFrom` | Auth.js не поддерживает сессии в БД вместе со входом по паролю. Отметка времени даёт отзыв сессий и мгновенное применение блокировки. Таблицы `Account`/`Session` не создаются: при входе только по паролю они не используются. |

## Что держит сама база, а не только код

Миграция `db_guards`. Проверки в приложении можно обойти сырым SQL или скриптом
миграции данных — эти нельзя:

- журнал действий: `UPDATE` и `DELETE` отбиваются триггером;
- `Settings`: ровно одна строка (`CHECK id = 1`);
- **правило 9.7**: сделка в статусе `VERLOREN` обязана иметь причину;
- выезд не может кончаться раньше, чем начался;
- ставка НДС в пределах 0–100 %, версия Angebot ≥ 1.

## Деньги и время

**Все суммы — целые числа центов.** Ни одного вычисления в дробных числах:
`0.1 + 0.2` в двоичной дроби даёт `0.30000000000000004`, и на сотне позиций
Angebot разойдётся со счётом на цент. Правило округления зафиксировано один
раз в `src/lib/money.ts`: коммерческое (половина уходит от нуля), позиция за
позицией, затем суммирование.

Ставка НДС хранится в базисных пунктах: 19,00 % → `1900`.

**Все даты хранятся в UTC и показываются в Europe/Berlin.** Германия дважды
в год переводит часы, и «09:00 у клиента» в марте и в ноябре — разное время
по UTC. Переходы на летнее и зимнее время покрыты тестами.

Сетка календаря строится по календарным суткам, а не прибавлением 24 часов:
в неделю с переводом часов одни сутки длятся 23 или 25 часов, и счёт
в миллисекундах промахнулся бы на день. Это тоже покрыто тестами.

## Предупреждение на Этап 2: нумерация счетов

Номер заявки `Deal.number` — последовательность Postgres, и в ней **бывают
пропуски**: откатившаяся транзакция значение не возвращает. Для заявок это
безразлично.

Для счетов — нет. Правило 9.5 запрещает пропуски в нумерации, поэтому номер
Rechnung обязан выдаваться строкой-счётчиком в `Settings` под `SELECT ... FOR
UPDATE` в той же транзакции, что и создание счёта. Последовательность для
счетов использовать нельзя.

## Установка на телефон

Приложение ставится **по ссылке, без App Store и Google Play** — так решено
главой 5.6 ТЗ, и это не компромисс:

- Apple отклоняет приложения, которые являются обёрткой вокруг сайта
  (правило 4.2 «Minimum Functionality»); внутренний инструмент для пяти
  человек через магазин не проходит;
- аккаунты разработчика стоят 99 $ в год у Apple и 25 $ разово у Google;
- каждое обновление проходит ревью по несколько дней, а здесь исправление
  доезжает до телефона монтажника сразу.

Внешне разницы нет: значок на домашнем экране, запуск на весь экран без
адресной строки браузера.

**Android, Chrome.** Открыть адрес платформы → меню (три точки) →
«Установить приложение».

**iPhone, Safari.** Открыть адрес платформы → «Поделиться» →
«На экран "Домой"». Обязательно Safari: другие браузеры на iOS этого не умеют.

Значки лежат в `public/icons` и сейчас являются **временным геометрическим
знаком**, а не логотипом фирмы. Когда появится настоящий логотип, положите
PNG с теми же именами или поправьте `scripts/generate-icons.ts` и запустите
`npm run icons`.

## Два входа

| Кто | Адрес | Вид |
|---|---|---|
| Офис (владелец, диспетчер) | `/login` | светлый экран для монитора |
| Бригада | `/m/anmelden` | тёмный экран во весь телефон |

Проверка одна и та же, различается только оформление и то, куда человек
попадает после входа. С каждого экрана есть ссылка на второй — на случай,
если открыли не тот.

Вход бригады **работает с выключенным JavaScript**: Next отдаёт форме
серверного действия обычную отправку методом POST. В подвале, где скрипты
могут не догрузиться, монтажник всё равно войдёт.

## Скорость

Замеры на сборке продакшена (`npm run smoke`):

| Показатель | Значение |
|---|---|
| Ответ сервера, медиана | 15 мс |
| Первая отрисовка | 72 мс |
| Первый заход, всего | 153 КБ |
| Повторный заход | 0 КБ — всё из кэша service worker |

Из чего состоит первый заход: 116 КБ скриптов (рантайм Next и React,
неустраним без смены архитектуры), 31 КБ шрифтов, 6 КБ прочего.

Шрифты были 153 КБ на 12 файлах: грузились два семейства, четыре
насыщенности и набор символов latin-ext. Узкое начертание из макета не
использовалось ни в одном компоненте, насыщенность 500 тоже, а latin-ext
нужен для восточноевропейских языков, которых у нас нет — немецкие ä ö ü ß
входят в основной набор. Осталось два файла и 31 КБ. Для телефона на слабой
связи каждый лишний файл шрифта — отдельное обращение к серверу.

## Что кэшируется, а что нет

Телефон монтажника могут потерять или передать другому человеку, поэтому
service worker (`public/sw.js`) устроен строго:

- **кэшируются** файлы сборки с хешем в имени, значки и страница «нет связи»;
- **никогда не кэшируются** страницы с данными, ответы Auth.js и всё, что
  не является запросом GET.

Адреса и телефоны клиентов не остаются в кэше браузера после выхода
из системы. Очередь отправки фотографий из офлайна появится вместе с
кабинетом монтажника (кусок 9) — она требует IndexedDB.

## Кабинет монтажника (глава 5.6 ТЗ)

Отдельное приложение в браузере телефона по адресу `/m`: свой вход
(`/m/anmelden`), тёмная оболочка, крупные кнопки. Офисного рельса нет — это
телефон в руке на объекте.

**Heute** — выезды на сегодня: время, адрес, этаж, телефон клиента, кнопка
навигации. Страница целиком серверная, клиентского кода на ней нет.

**Auftrag** — объём работ, заметка диспетчера, парковка, состав бригады. Цены
здесь нет и быть не может: запрос её не выбирает вовсе (глава 4 ТЗ), а не
скрывает в разметке.

### Статусы одним тапом

Unterwegs → Angekommen → In Arbeit → Fertig. Кнопка одна и всегда показывает
следующий шаг. Назад статус не откатывается: отметка «выехал в 8:10» — факт,
на который опирается расчёт зарплаты, а не черновик. Отмена выезда — дело
диспетчера и делается в календаре.

### Фотографии и очередь отправки

Требование ТЗ: минимум по два снимка «до» и «после», и работа при плохой связи
в подвале. Поэтому снимок сначала ложится в IndexedDB телефона и только потом
уходит на сервер. Закрытая страница, потерянная сеть и лифт без связи ничего
не теряют: очередь дожимается при следующем открытии кабинета и по событию
`online`.

Повторная отправка безопасна: у каждого снимка есть `clientKey`, присвоенный
телефоном, и сервер по нему узнаёт уже принятый файл. Два пути — обычная форма
(работает без JavaScript) и очередь — проходят через одну функцию
`src/server/jobs/photos.ts`, поэтому правила у них общие.

Тип файла определяется по первым байтам, а не по имени и не по заголовку
от клиента: под именем `foto.jpg` приходит что угодно.

### Минимум фотографий проверяет сервер

| Переход | Что требуется |
|---|---|
| → In Arbeit | снимки «до» (по умолчанию 2) |
| → Fertig | снимки «после» (по умолчанию 2) |
| Abnahme | снимки «после» |

Числа задаёт владелец в настройках (`minPhotosBefore`, `minPhotosAfter`).
Снимать «до» после сборки кухни уже поздно — поэтому «до» спрашиваются
на входе в работу, а не в конце.

### Учёт времени

Старт и стоп; длительность считает сервер, с телефона она не приходит — время
идёт в расчёт зарплаты, а часы на телефоне легко перевести. Второй таймер
одновременно не запускается: система называет выезд, на котором время уже
идёт. Подпись протокола и статус «Fertig» закрывают незакрытые записи сами.
Остановить идущий таймер можно всегда, даже на закрытом выезде: иначе его
некому закрыть, и он до вечера копит минуты.

### Материал и доплата

«Докупили силикон 12 €», «добавились 2 полки, +40 мин» — уходит владельцу
на панель «Heute». Это **сообщение, а не изменение цены**: решение принимает
только владелец (глава 4 ТЗ), и сумма заказа от согласования не меняется —
цену владелец ставит отдельным действием.

## Abnahmeprotokoll — приёмка (глава 5.6.5 ТЗ)

Отдельный экран `/m/auftrag/<id>/abnahme`: чек-лист выполненного, поле
замечаний, согласие на фотофиксацию и подпись клиента пальцем на экране.

Подпись рисуется на `canvas` указательными событиями (палец, стилус, мышь)
и уходит PNG с прозрачным фоном. Прозрачность не украшение: по ней сервер
отличает подпись от пустого холста — иначе протокол подписывался бы пустым
прямоугольником. Проверка — `src/lib/signature.ts`, покрыта тестами.

После подписи создаётся запись `Handover`, собирается PDF и **всё
блокируется**: фотографии, статус, повторная приёмка. Подписанный документ
у клиента на руках, и переписывать его нельзя.

Приёмка закрывает правило 9.4: заявка переходит в «Ausgeführt» автоматически,
когда закончены все её выезды, и проверка правила вызывается честно — если
чего-то не хватает, заявка остаётся в прежней колонке.

Без JavaScript подпись невозможна в принципе, и страница говорит об этом
прямо, а не делает вид, что работает.

## PDF: предложение и протокол

Глава 5.4 ТЗ требует два вывода предложения — текст для WhatsApp и PDF.
Документы собирает `@react-pdf/renderer` на сервере, встроенным шрифтом
Helvetica: умлауты и «ß» в нём есть (кодировка WinAnsi), внешние файлы
шрифтов в образ тащить не нужно. Документы всегда по-немецки, независимо
от языка интерфейса: их читает клиент и бухгалтер, а не сотрудник.

PDF предложения собирается один раз при отправке и кладётся в хранилище.
Суммы и правовые блоки берутся из самого предложения, а не из настроек:
предложение — снимок на момент отправки, и документ должен показывать ровно
то, что получил клиент.

Маршруты: `/api/angebote/<id>/pdf` для сотрудников (роль Monteur получает 404 —
в документе цены) и `/angebot/<токен>/pdf` для клиента по публичной ссылке.

**Тонкость сборки.** `pdfkit` подгружает данные встроенных шрифтов обычным
`require` по вычисляемому пути, и трассировщик Next такие обращения не видит.
Без `outputFileTracingIncludes` в `next.config.ts` PDF ломался бы только
в продакшене — в разработке файлы лежат в `node_modules`. Проверено: сборка
standalone падала с `MODULE_NOT_FOUND pdfkit/js/standard-fonts/Helvetica.cjs`.

## Файлы: фотографии, подписи, документы

Два драйвера за одним интерфейсом (`src/lib/storage`): том на диске (сейчас)
и S3-совместимое хранилище. Переезд — смена `STORAGE_DRIVER` и перенос файлов.
Для S3 регион проверяется на европейский: ошибиться при настройке слишком
легко, а глава 3 ТЗ требует ЕС.

Файлы **никогда не отдаются напрямую из хранилища**. Доступ идёт через
`/api/files/<ключ>`, где проверяются права: владелец и диспетчер видят всё,
монтажник — только свои выезды. «Нет прав» и «нет файла» отвечают одинаково:
иначе по кодам ответа можно перебором узнать, какие выезды существуют.

## Приём заявок с сайта

`POST /api/webhook/lead` с подписью HMAC-SHA256 в заголовках
`X-MS24-Signature` и `X-MS24-Timestamp`. Метка времени входит в подпись:
иначе перехваченный запрос можно было бы отправлять повторно, и каждая
отправка создавала бы заявку. Допуск — 5 минут.

Без `LEAD_WEBHOOK_SECRET` эндпоинт закрыт (503): открытый приём заявок
означал бы мусор в доске у первого же сканера портов.

Клиент ищется по нормализованному телефону и почте — с сайта пишет тот же
человек, что уже звонил, и второй карточки быть не должно. Повторная отправка
той же формы в течение 10 минут не создаёт дубля. Чек-лист заявки сразу
отмечает, чего в ней не хватает.

## Предложения клиенту (Angebote)

Конструктор из главы 5.4 ТЗ: позиции из каталога услуг или вручную,
количество, единица, цена. Суммы и НДС считает **сервер** при сохранении:
показать клиенту одну цифру, а хранить другую — верный способ получить
расхождение в документе.

Готовое предложение выводится в трёх видах: **текст для WhatsApp** с кнопкой
копирования, **PDF** и **публичная страница** для клиента. Версии нумеруются: v1, v2,
v3 — отправленное предложение не правится, выпускается новая версия, а
прежние помечаются заменёнными.

### Два жёстких запрета

| Правило | Что запрещено | Где проверяется |
|---|---|---|
| **9.1** | отправить Angebot без цены, подтверждённой владельцем | `checkCanSend` в момент отправки |
| **9.2** | сохранить Angebot без блока гарантии и просьбы о парковке | `checkLegalBlocks` при каждом сохранении |

Правило 9.2 проверяется дважды: сначала что блоки заполнены в настройках
фирмы, затем что они действительно попали в документ. Второе не формальность:
тексты копируются в Angebot снимком, и пустая копия при заполненных
настройках означала бы ошибку в коде.

Признак «цена подтверждена» снимается при любом изменении цены. Поэтому
«цена есть, но флаг снят» — это правка, которую владелец ещё не видел, и
такое предложение не уйдёт.

### Правовые блоки

Три блока — гарантия, просьба о парковке, оговорка об объёме — живут в
настройках фирмы и попадают в каждое предложение.

При первом открытии настроек форма **предлагает** готовые немецкие
формулировки, но **в базу они не попадают, пока владелец не прочитает их и
не нажмёт «Сохранить»**. Тексты говорят от лица фирмы и обещают клиенту
гарантию — записывать такое без прочтения человеком нельзя. Пока блоки пусты,
правило 9.2 не даёт сохранить ни одного предложения, и это намеренно.

Формулировки не заменяют юриста. Перед первой отправкой клиенту их стоит
показать своему Steuerberater или адвокату.

### Публичная ссылка

Клиент открывает предложение без входа в систему, по неугадываемому токену
в 24 случайных байта. Кнопка «принять» фиксирует **дату и IP** (глава 5.4).
Ответить можно один раз; принятие переводит заявку в колонку «Bestätigt».

На этой странице нет ни навигации, ни ссылок внутрь платформы: клиент видит
только своё предложение.

## Каталог услуг и настройки фирмы

`Einstellungen → Firma` — реквизиты по §14 UStG, налоговый режим, ставка НДС,
Stundensatz, правовые блоки, зазор между выездами, минимум фотографий.
Переключение в режим **Kleinunternehmer (§19 UStG)** обнуляет ставку и
добавляет в документы обязательную оговорку.

`Einstellungen → Leistungen` — прайс фирмы. Пустой при первом запуске: цен
в коде и в сидах нет намеренно, это настоящий прайс, а не пример.

## Календарь и диспетчеризация

План работ из главы 5.3 ТЗ: по горизонтали дни, по вертикали бригады.
Виды «неделя» и «день». Карточка выезда окрашена по виду работ. Страница
целиком серверная — **154 байта клиентского JavaScript**.

**Бригады** заводит владелец в разделе «Kolonnen». Бригада — это строка
календаря: «Team 1», «Team 2», «Ivan». Тот, кто ездит один, тоже бригада.
Удаления нет, только отключение: на бригаду ссылаются прошлые выезды.

Выезды планируются **в карточке заявки**, а не в календаре: там уже есть
клиент, адрес и объём работ. Запланированный выезд сам переводит заявку в
колонку «Termin geplant» — иначе доска разошлась бы с календарём.

### Конфликты — предупреждение, а не запрет

Система показывает два вида конфликтов и даёт диспетчеру решить:

- **бригада уже занята** в это время другим заказом;
- **между выездами по разным адресам меньше времени, чем нужно на переезд**.

Оба сохраняются только после галочки «планировать всё равно», и факт
планирования вопреки предупреждению попадает в журнал. Запрещать нельзя:
соседний подъезд иногда стоит наложения, и это знает диспетчер, а не
программа.

Два заказа **по одному адресу** переезда не требуют и конфликтом не считаются.

Зазор задан числом минут в настройках, а не расстоянием: расчёт расстояния
требует геокодинга, то есть внешнего сервиса и отдельного согласия по DSGVO.
Фиксированный зазор честно работает уже сегодня.

### Что запрещено жёстко

Правило 9.3 ТЗ: **выезд невозможен без адреса и без фамилии либо фирмы
клиента.** Это отказ, а не предупреждение, и проверяется в момент создания
выезда — там же, где и при переводе заявки в колонку «Termin geplant».

## Заявки и канбан

Доска из главы 5.2 ТЗ: девять колонок от `Neu` до `Bezahlt` плюс `Verloren`
отдельно. Карточка заявки содержит клиента, адрес, виды работ, источник,
ожидаемую длительность, чек-лист «что уточнить» и ленту событий.

Перевод между колонками — выпадающим списком, а не перетаскиванием.
Перетаскивание требует клиентской библиотеки, плохо работает пальцем на
телефоне и не работает вовсе до загрузки скриптов. Список работает везде.
Страница доски содержит **152 байта клиентского JavaScript**.

**Источник заявки — обязательное поле.** Без него не посчитать, какой канал
приносит деньги, а это одна из четырёх измеримых целей главы 1 ТЗ.

**Первый ответ отмечается одним нажатием и только один раз.** Цель главы 1 —
меньше 15 минут; в журнал пишется, сколько минут прошло с момента заявки.
Карточка без отмеченного ответа показывает счётчик времени, красный после
30 минут (глава 5.1).

### Цену ставит только владелец

Жёсткое требование главы 4 ТЗ, реализованное в двух местах сразу:

- **страница** не выводит форму цены никому, кроме роли `INHABER`;
- **серверное действие** независимо проверяет роль через `assertCanSetPrice`
  и бросает исключение.

Одного рубежа мало: скрытую форму можно отправить вручную, а спрятанное
в разметке значение видно через «просмотр кода страницы».

Установка цены сразу ставит признак «подтверждена владельцем» — он понадобится
правилу 9.1, когда появятся Angebot. Очистка поля снимает и цену, и
подтверждение. Каждое изменение цены попадает в неизменяемый журнал со старым
и новым значением.

Монтажник цену не видит вообще: в слое запросов для роли `MONTEUR` поля цены
**не включаются в выборку** — значение физически не покидает базу.

### Правила главы 9 на доске

| Правило | Что запрещено | Где проверяется |
|---|---|---|
| 9.3 | `Termin geplant` без адреса и без фамилии либо фирмы клиента | `checkTransitionSync` |
| 9.4 | `Ausgeführt` без протокола приёмки и без нужного числа фото «после» | `checkTransition` |
| 9.7 | `Verloren` без причины | `checkTransitionSync` + ограничение в базе |

Возврат заявки из `Verloren` в работу стирает причину: иначе в карточке
активной заявки осталось бы «слишком дорого».

Колонка `Ausgeführt` недостижима, пока не построен кабинет монтажника
(кусок 9): без фотографий и подписанного протокола объявить работу сданной
нельзя, и это правильно, а не недоделка.

## Клиенты и адреса

Раздел «Kunden» (глава 5.10 ТЗ): карточка клиента, несколько адресов,
история заказов, метки и внутренние заметки.

**Поиск находит клиента по любому написанию номера.** Один берлинский
номер приходит в систему как `+49 176 79892037`, `0176/79892037`,
`0049 176 79892037` или `017679892037`. Рядом с введённым значением
хранится нормализованная форма — только цифры в международном виде — и
поиск идёт по ней, по индексу. Введённое написание при этом сохраняется:
терять то, что записал диспетчер, нельзя.

Поиск также работает по имени, фамилии, названию фирмы, почте, улице,
городу и индексу. Он сделан обычной формой с методом GET: работает до
загрузки скриптов, результат можно отправить коллеге ссылкой, а отбор
делает база, а не браузер.

Страница списка содержит **149 байт клиентского JavaScript** — она целиком
серверная.

### Löschkonzept (глава 3 ТЗ)

Два разных действия, и их нельзя путать:

| Действие | Кто | Что происходит | Обратимо |
|---|---|---|---|
| Архивировать | владелец, диспетчер | клиент пропадает из списков, данные на месте | да |
| Удалить персональные данные | **только владелец** | имя, контакты, заметки и улица стираются навсегда | **нет** |

Удаление требует ввести слово `LÖSCHEN`: случайный клик не должен стирать
данные необратимо. Сама запись клиента и его заказы остаются — счета и всё,
связанное с налогами, хранится по закону годами.

Город и индекс адреса при удалении сохраняются: по ним считается статистика
по районам, а опознать человека по «10115 Berlin» нельзя.

В журнал пишется факт удаления, но не то, что было удалено — иначе
персональные данные остались бы в неизменяемом журнале навсегда.

## Вход и права

| Что | Как сделано |
|---|---|
| Пароли | scrypt из `node:crypto`, параметры записаны в самой строке хеша — их можно усилить позже, не ломая существующие пароли |
| Второй фактор | TOTP (RFC 6238), совместим с Google Authenticator и аналогами. Секрет в базе зашифрован AES-256-GCM ключом `ENCRYPTION_KEY` |
| Коды восстановления | десять штук, в базе только хеши, каждый срабатывает один раз |
| Сессии | JWT, срок из `SESSION_MAX_AGE_SECONDS` (по умолчанию 8 часов) |
| Отзыв сессий | `User.sessionsValidFrom`. Отключение сотрудника, смена роли и смена пароля выбрасывают его немедленно, а не через 8 часов |
| Перебор паролей | не более 8 неудачных попыток на email за 15 минут |
| Журнал | вход, неудачный вход, использование кода восстановления, все изменения сотрудников |

Проверка роли идёт в двух местах, и это не дублирование:

- **middleware** отсекает по адресу, опираясь только на токен (базы в edge-среде
  нет) — быстро и грубо;
- **`requireUser()` / `requireRole()`** читают состояние из базы на каждом
  обращении — это авторитетная проверка. Токен отключённого сотрудника
  middleware пропустил бы до истечения срока.

Скрытые пункты меню защитой не считаются.

## Образ проверен сборкой

Образ `runner` собирается и запускается: миграции применяются из образа
`tools`, `npm run create-user` в нём работает, приложение отвечает и переходит
в состояние `healthy`, вебхук заявок принимает подписанный запрос и отвергает
неподписанный, PDF внутри образа собирается встроенным шрифтом.

Две вещи, найденные именно этой проверкой и исправленные:

- `prisma generate` на стадии сборки падал без `DATABASE_URL` — `prisma.config.ts`
  намеренно требует строку подключения. В стадию `builder` добавлена фиктивная
  строка: она нужна только генератору, к базе он не обращается, и в рабочий
  образ значение не попадает. Без этого первый же `docker compose up --build`
  на сервере заканчивался ошибкой;
- данные встроенных шрифтов `pdfkit` не попадали в standalone-сборку
  (см. раздел про PDF).

## Известные решения, требующие подтверждения

- **Шрифт.** У Barlow из макета нет кириллического начертания. Немецкий
  интерфейс выглядит как в макете, русский рисуется следующим шрифтом стека.
- **Auth.js v5 в статусе beta.** Стабильная ветка v4 работает только со старым
  Pages Router. Версия зафиксирована точно, без `^`.
- **Prisma 7.10.0** закреплена явно: в теге `latest` у npm сейчас стоит
  release candidate 8.x.
- **Предупреждение при сборке** `CompressionStream ... not supported in the Edge
  Runtime` из библиотеки `jose` — безобидное: этот путь используется только для
  сжатых токенов, которых Auth.js не выпускает.

---

## Сотрудников не удаляют

Внешний ключ `ActivityLog.userId` объявлен с `onDelete: Restrict`. Удалить
сотрудника, у которого есть записи в журнале, база не даст — и это намеренно:
журнал действий не должен терять автора. Вместо удаления сотрудника отключают
(`active = false`), а по требованию DSGVO его данные обезличиваются; записи
журнала продолжают ссылаться на обезличенную учётную запись.

Без `Restrict` попытка удаления запускала бы `SET NULL` на журнале, то есть
`UPDATE`, который запрещён триггером неизменяемости, — и падала бы невнятной
ошибкой из глубины базы.
